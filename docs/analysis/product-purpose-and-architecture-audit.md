# SYNTH: purpose, architectural fit, and a development goal

**Date:** 2026-10-15 (America/Hermosillo)

**Status:** independent, read-only product/architecture audit; recommendation, **not** a new expedition, approved design, implementation, or acceptance verdict.

**Snapshot:** `arena/d5e4625c-synth` at `86a66dc39b0271021ed786ccbfad9207d5cb1752`; draft [PR #346](https://github.com/synth-framework/synth/pull/346) targets `main`. Counts and checks below are snapshot-specific. This report does not authorize changing the branch policy, completing CLI-003, starting STATE-001, merging the PR, or changing LIFE-002's status.

## Short answer

SYNTH's *plausible problem* is not “we need an event store.” It is that engineering teams and AI agents lose the **intent, constraints, approval, and evidence** linking a request to a code change, and may proceed when that link is unclear. A good product would help a human determine what was requested, what was approved, what changed, what was checked, and whether it is safe to merge—across sessions and branches.

**Verdict:** the problem is credible; the current architecture is **conditionally appropriate but not yet justified as the default solution**. Git branches, PR review, required CI and a small amount of structured, in-repo decision/evidence metadata already cover much of this need. SYNTH adds domain-specific transitions, deterministic replay of its *own governance state*, and policy checks. Those are potentially valuable when enforceable pre-execution authorization and independently reconstructible decisions are required. They do not prove the software itself is correct, eliminate the Git publication boundary, or show that users can complete the workflow more reliably than with a simpler baseline. The critical unsolved design question is how independent branches append to one global event chain without publishing an invalid merged history.

**Recommendation:** make a small, Git-native operator outcome the development goal, compare it against an ordinary PR+CI baseline with the *same users and task*, and retain only the extra SYNTH machinery that wins on a specified assurance or usability measure. Do not implement another permanent governing branch, synchronization ritual, or database as an architectural reflex. Preserve the existing records while testing this proposition.

## 1. What the project actually claims to be

The [introduction](../guides/philosophy/00-introduction.md) names the problem as fragile engineering knowledge—decisions, assumptions, constraints, discoveries and dead ends scattered across people and documents. The [README](../../README.md) summarizes the intended division of labor as “Humans explore. SYNTH remembers. AI executes deterministically.” Its public model is **Mission → Expedition → Evidence / Plan → Event → State → Replay**; it expressly says it is not itself an AI agent or code generator. The stronger [architectural constitution](../architecture/constitution.md) proposes one mutation authority, governance before execution, replayable transitions, and cryptographic authorization. Those are design commitments, not evidence that every real-world code change or deployment is governed.

A more precise, testable interpretation is: **a Git-adjacent governance layer for human/AI engineering work**. Humans approve bounded intent; an operator/agent works on a branch; SYNTH records governance transitions, evidence and state; replay checks those records; Git/PR/CI publishes and tests the code. It is *not* literal replay of the agent's reasoning or execution of arbitrary source edits. This is a product hypothesis synthesized from the docs, not a statement of established user demand.

### Current implementation and the actual boundary

- The CLI exposes **33 top-level command families** (`node dist/cli/entry.js --help --json` at the snapshot), while the [getting-started guide](../operator/01-getting-started.md) starts with `mission create` / `mission approve` and the [first-expedition guide](../operator/02-your-first-expedition.md) and supposedly canonical [operator journey](../operator/13-operator-journey.md) teach direct JavaScript API calls and a different lifecycle. A previous [simplification decision](simplified-interaction-model-decision.md) proposes still another public vocabulary. That proposal is not the shipped CLI. The first-time operator contract is therefore not settled.
- The implemented [ExecutionGate](../../src/control/execution-gate.ts) validates capabilities/policy, constructs events, optionally signs them, appends them and rebuilds/commits state. The [event store](../../src/infra/event-store.ts) and [state store](../../src/infra/state-store.ts) persist domain records. [Replay](../../src/runtime/replay.ts) and `verify` test the recorded domain state, not the correctness of unrecorded code edits or an external deployment. Signing is **opt-in** in ExecutionGate; [key-store](../../src/signing/key-store.ts) locates private keys outside the repository by default. Do not interpret a passing replay check as universal authorization or tamper resistance against someone who controls the repository/keys.
- Git remains a separate boundary. [The configured ledger branch](../../.synth/config.yaml) is this Arena session branch, and [the branch resolver](../../src/ledger/branch.ts) currently supports configured/recorded branches with fallback. The [2026-10-15 ADR-055 update](../adr/ADR-055-ceremonial-events.md#2026-10-15-design-update--git-native-publication-not-implemented) replaces the old shared-ledger **design direction** with branch-local records → ordinary reviewed PR → `main` publication → explicit update on other branches. This is **not implemented as a safe divergent-chain integration protocol**. A pushed work branch is reviewable but not published on `main`; neither a local approval nor a successful local replay changes that.
- Current self-use is substantial for governance records: four segment files contain **506 events** of 27 types; the current aggregate has **5 missions** and **71 expeditions** (34 completed, 17 draft, 8 committed, 6 approved, 5 cancelled, 1 executing). Of the events, 76 are expedition creations, 74 evidence attachments, 51 approvals, 45 commitments, 36 starts, 34 completions, and only 4 each are deliveries and integrations. There are **no `OBJECTIVE_ADDED` events** in this repository's 506-event history. This describes *this repository's use*, not all SYNTH installations; it suggests the documented objectives-heavy journey is not the journey mainly exercised here.
- At this snapshot `status`, `explain replay`, `doctor`, `verify` and `checkpoint` all returned `ok`; replay reports a valid chain/consistent state and `verify` passes **6/6** checks. This is concrete evidence that today's **local recorded history** is coherent. `doctor` reports “no anchor to compare,” not that cross-branch publication is correct. `status` simultaneously emits **32 warnings**, including **30 delivery-pending** warnings for historic completed expeditions. A clean health result and an overwhelming work queue can both be true; the latter may include old pre-delivery semantics and needs triage, not automatic mass sealing.
- There is meaningful engineering depth: **400 source TypeScript files**, **248 test JavaScript files**, **178 task JSON definitions** and **119 literal `test:all` chain steps**. Quantity alone is not outcome evidence. The [CLI-003 evidence](../../proof/expeditions/e47a186cb472a20a/attachments/evidence-cli-003-windows-and-timing.md) records full-chain success, native Windows *targeted* checkout/task coverage, and a clean latest-host sample of **40.1 ms version / 178.0 ms status / 117.7 ms replay**. The existing absolute targets remain **45 / 130 / 110 ms** respectively; the last two were **not met**. CLI-003 remains executing. Do not substitute old, incomparable timing samples or claim Windows coverage of every verb.

**Epistemic limit:** these observations are source inspection, this checkout's records and targeted tests; no independent user interviews, external customer retention data, full security review, or two-branch integration experiment was performed for this audit. CI for PR #346 had passing `generate`, `plan`, `portable-tasks` and pending `execute`/`proof` when checked; that is *not* an all-green PR claim.

## 2. The simpler control: what Git/PR/CI already buys

GitHub's ordinary PR workflow is branch → commit → review proposal → merge into base; a remote branch does not make its content the base branch's content [1](https://github.com/github/docs/blob/main/content/pull-requests/get-started/pull-request-quickstart.md). Branch protection can require reviews, checks and freshness before merge [1](https://github.com/github/docs/blob/main/content/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule.md). These are available without SYNTH. A draft PR cannot merge [2](https://github.com/github/docs/blob/main/content/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request.md).

**Baseline to beat:** one issue/request (goal and acceptance checks), one work branch, a short tracked decision/evidence file or PR template (intent, constraints, approver, test links), a PR against `main`, required CI and review, and explicit fetch/update on other branches. CI can validate structured metadata and cross-link the relevant commits and results. This gives durable history and an auditable *publication* boundary, though it does not by itself enforce a machine-readable pre-execution policy or reconstruct a domain state from semantic events. Do not silently assume this baseline requires no maintenance: human discipline, schema validation and branch protection configuration matter.

Backstage illustrates the smaller design space: human-editable YAML entity descriptors with a stable schema and ownership/lifecycle fields, rather than an event-sourced control plane [1](https://github.com/backstage/backstage/blob/master/docs/features/software-catalog/descriptor-format.md). Renovate's optional dependency dashboard illustrates a pre-PR human approval queue, not a reason to create a second publication authority [1](https://github.com/renovatebot/renovate/blob/main/docs/usage/key-concepts/dashboard.md#dependency-dashboard-approval-workflow). Atlantis separates plan and apply requirements; approvals and freshness can be checked at different moments [1](https://github.com/runatlantis/atlantis/blob/main/runatlantis.io/docs/server-side-repo-config.md). These are **analogies, not substitutes for a reproducible governance journal**. OpenGitOps emphasizes versioned desired state, agent pull and continuous reconciliation [1](https://github.com/open-gitops/documents/blob/main/PRINCIPLES.md); SYNTH currently demonstrates local record validation, **not** such a cross-session reconciliation loop. An optional GitHub merge queue checks PRs against a fresh base but does not resolve a domain event hash-chain fork by itself [1](https://github.com/github/docs/blob/main/content/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue.md).

| Candidate | What it solves well | Where it is weak / cost | Decision now |
|---|---|---|---|
| **Git + PR + CI + structured decision/evidence file** | Plain publication, diff/review, portable handoff, low conceptual load | No semantic replay; pre-execution policy may be advisory or CI-enforced only at merge | **Control group**; ship/measure first |
| **Current SYNTH on top of Git** | Bounded lifecycle and domain checks; recorded decisions; consistent replay on one history | CLI/documentation mismatch; 30 historic pending deliveries; local health ≠ merge safety; cost of global history/projections | Preserve/test; **do not claim general superiority yet** |
| **SYNTH with Git-native branch-local records** | Could make decision records part of ordinary PR and keep one publication boundary | Requires fail-closed divergent-chain handling, preservation of historical provenance and a migration; design only today | Conditional next step **if** baseline cannot supply necessary assurances |
| **Database / permanent shared ledger branch / automatic cross-branch sync** | May help a truly concurrent multi-writer product | Adds another availability, authority and synchronization plane; contradicts simple Git handoff by default | **Not justified by current evidence** |

## 3. Architectural fit: strengths and liabilities

1. **Genuine strength: explicit, replayable domain decisions.** A deterministic event journal can distinguish “approved,” “started,” “evidence attached,” and “integrated” in a way an unstructured commit message cannot. The local 506-event replay and 6/6 verification are positive *integrity of recorded governance state* evidence. Keep this if it changes an actual operator decision or catches a failure the baseline misses.
2. **Most important correctness gap: concurrent Git histories.** The [ADR-055 analysis](../adr/ADR-055-ceremonial-events.md) documents that two independently appended branches each extend the same global `previousHash`. Git text merging segments/projections does not turn those into one valid chain. A branch-local PR design must either (a) serialize ledger-bearing integrations and reject a stale PR, with a **governed** update/re-proposal path, or (b) explicitly redesign event identity/streams and prove an integrated projection with provenance. “Flip `git.ledgerBranch` to `main`,” “rebase the JSON,” and “merge queue fixes it” are not valid proofs. Do **not** weaken replay checks or hand-edit canonical state to make a merge pass. This is a design risk, not evidence that the current branch is corrupt.
3. **Operator friction is part of correctness.** Seven advertised concepts do not translate to a seven-action journey. The three starter/operator texts disagree; current help lists 33 families. `status`'s 30 historical delivery warnings show that a precise model can still obscure the *next relevant action*. [Prior consolidation work](synth-consolidation-review.md) advocates hiding internal governance mechanics; its claim that all of them are indispensable is a hypothesis, not a result. Fold redundant delivery ceremonies only after preserving their useful assertions; [LIFE-002](../../.synth/data/expeditions/f0912d1aeee16213.json) is draft and has a dated Git-native refinement, not a shipped simplification.
4. **Costs are measurable, not a database mandate.** The [preliminary state-access audit](state-access-preliminary.md) on an older **505-event** snapshot traced **39 reads / 1.64 MB** for `status` and **80 projection writes** for one copied `RefineExpedition`, **77** of which retained identical content. It explicitly does *not* measure a Git-backed CLI mutation end-to-end, prove a database is needed, or settle CLI-003 timing. Microsoft's CQRS guidance likewise notes view-rebuild advantages and complexity/eventual consistency costs [1](https://github.com/microsoftdocs/architecture-center/blob/main/docs/patterns/cqrs.md). Prioritize redundant work/unchanged writes and an intelligible operator path before adding storage infrastructure. STATE-001 is approved but cannot simply start on CLI-003's owned session branch under the current branch policy.
5. **Assurance language must be narrower.** Constitution-level “every mutation,” “cryptographic proof” and “structurally impossible” are requirements, not externally demonstrated guarantees for arbitrary Git edits. The current `verify` JSON checks replay/projection/evidence/provenance/invariants/drift; it does not report that PR integration, identity ownership, or external actions were verified. Opt-in event signing and Git review can be useful *layers*; neither substitutes for independent trust anchors, a threat model, or checking the deployed result. Distinguish **recorded event integrity**, **authorized transition**, **PR publication**, **CI test evidence**, and **runtime outcome** in every status claim.
6. **Tests are strong in places, but coverage truth is a separate issue.** Targeted `node --test tests/ledger-delivery.test.js tests/ledger-ceremony.test.js tests/no-write-on-read.test.js` passed **26/26** in this audit, supporting local ceremony/read-only behavior. The [testing infrastructure review](../plans/testing-and-reporting-infrastructure-review.md) and CLI-003's [46 consumer-suite review](../../proof/expeditions/e47a186cb472a20a/attachments/evidence-cli-003-windows-and-timing.md) identify pre-existing orphaned red tests (32 green / 14 pre-existing red in the latter scope). A passing chained test task must not be paraphrased as “all test files pass.” No broad suite or real two-branch merge test was rerun for this report.

## 4. Proposed product goal and falsification test

> **Goal hypothesis:** For a team doing human-approved AI-assisted repository work, SYNTH makes the *intent → approval → code/evidence → PR → published outcome* link easier to understand and harder to accidentally misrepresent than ordinary Git+PR+CI, **without adding a second publication ritual**. Operators can recover the correct next step in a fresh session; maintainers can prove what a check actually checked. If SYNTH cannot show an incremental gain over the baseline, prefer the baseline and simplify or retire the extra machinery from the default path.

Do not adopt this goal as settled product truth without talking to prospective users. A first experiment can use a realistic ambiguous change request and a two-branch conflict, not the project's own happy-path example. Pre-register the task, participants, environment, protected-branch settings, and pass criteria. Run the **same task** with the baseline and with SYNTH; record full commands, elapsed time, interventions, confusion/errors, and *actual* caught/uncaught faults. Do not infer a general population effect from one internal operator or synthetic tests.

**Candidate acceptance rubric (proposed, not existing expedition criteria):**

- **Safety:** in a controlled two-branch case, independently appended histories cannot be silently published as valid; integration either retains one provable history with provenance or fails with a clear recovery action. No source or canonical-state hand edits to pass. CI and the current checkout agree on the *published* revision being checked.
- **Truthfulness:** given a fresh session/clone, an operator can distinguish local approval, pushed review branch and published `main` state; `status` shows the relevant next action rather than repeating 30 legacy obligations as immediate work. Evidence links to the exact PR/head, tests run and acceptance result. Failure is explicit, not a green summary hiding unrun checks.
- **Usability:** in a preliminary pilot, at least three unfamiliar operators independently complete a bounded request and locate its approval/evidence in both treatments; target **3/3 unassisted, correct publication-state answers** with SYNTH. Compare completion, wrong-branch/incorrect-publication errors, assistance requests and time to recover. A provisional go/no-go bar is **at least one material authorization/publication error caught by SYNTH that the configured baseline misses, with no more than 20% additional median operator time**, *or* an independently observed reduction in operator errors/time at equal safety. Agree on the fault and timing protocol **before** the trial. Three users are a diagnostic pilot, not a statistically generalizable claim. If neither bar is met, default to the simpler path.
- **Performance:** do not move the **existing** CLI-003 thresholds to win this audit. Version ≤45 ms, status ≤130 ms and replay ≤110 ms must be evaluated with its same-session control/clean-and-dirty qualification; last recorded sample missed the latter two. State-I/O optimizations should be measured separately and must not skip validation.
- **Scope:** record what SYNTH cannot attest (unrecorded edits, non-Git deployment, external identity) as plainly as what it can; no blanket “replay proves the software correct” marketing claim.

## 5. Road toward the goal, with stop conditions

| Phase | Deliverable and verification | Dependency / stop rule |
|---|---|---|
| **0. Frame the problem and control** | Interview intended operators about lost-context and unsafe-authorization incidents; select one representative request; run the Git+PR+CI+small-metadata baseline first. Record the measurement protocol and actual protected-branch configuration. | **Stop** if there is no demonstrated problem or no plausible incremental SYNTH assurance. This is research, not a mandate to modify governance history. |
| **1. Make publication correct** | Specify branch-local/private vs pushed/reviewable vs `main`-published records; build a disposable two-branch test proving fail-closed stale-chain behavior and a governed recovery with provenance. Decide whether to serialize integrations or change the event model on evidence, not aesthetics. Correct LIFE-002 draft append-only before approving it; migrate session-scoped config/consumers explicitly. | Blocking for any claim that Git-native event integration works. No permanent shared governing branch or second approval prompt by default. Do not relax branch ownership, hand-merge the journal, or pretend design-only ADR text is code. |
| **2. Make the operator path boring** | Align README, quickstart and canonical journey with one *shipped* CLI walkthrough; show one context-aware action and why. Triage historic delivery warnings and audit CLI verbs via CLEAN-001 **KEEP/SIMPLIFY/REPLACE/REMOVE**, not blanket deletion. Fold adapter config into LIFE-002; preserve no-VCS assertions and explicit `--no-push` on canonical branches. | Measure novice comprehension against phase 0; never trade away provenance or lifecycle checks merely to shorten the list. Keep historical records append-only. |
| **3. Improve cost without changing the contract** | Finish CLI-003 timing honestly; investigate STATE-001's measured duplicate reads/unchanged writes in a separately authorized branch/session. Prove parity, crash/concurrency behavior and no-write-on-read. Tighten test-inventory reporting so chained green and orphan reds are distinguishable. | STATE-001 is approved **not executing**; this checkout is owned by executing CLI-003. Do not start it by bypassing the declared-branch guard or close CLI-003 to clear a scheduling obstacle. |
| **4. Decide whether SYNTH is the product** | Re-run the matched-user comparison and two-branch adversarial test on the implemented path. Publish benefit, burden, limitations and a decision: keep a small in-repo governance layer; invest in deeper event sourcing only if it wins on explicit needs; or revert to Git+metadata/CI as the default. | No broad rollout or stronger assurance language until the comparison and safety test support it. Preserve existing historical records regardless of product-surface decision. |

**Decision requested of the project owner:** Is the target customer a team that merely needs durable, reviewable rationale, or a team that must *technically prevent* an agent from proceeding without a recorded pre-execution authorization? The baseline handles the first well; the second may justify SYNTH's extra authority/replay model. The experiment should test that distinction instead of assuming the answer.
