# SVG board utility: input-format standards and options

**2026-10-15 — research and recommendation, not an approved schema or implementation.** The owner asked what could replace or complement Markdown for the real pilot utility. The privately supplied SVG examples are treated as reference outputs, not copied or linked in this public report. This work is not a canonical SYNTH Expedition and does not authorize implementation on CLI-003's branch.

## What is standardized, and what is not

- **Design tokens:** The Design Tokens Community Group's stable **Format Module 2025.10** specifies a JSON exchange format for typed tokens, grouping, references and metadata (`$value`, `$type`, `$description`). It explicitly says it is a **Final Community Group Report, not a W3C Standard or W3C Recommendation**. It is a sensible portable input for colours, dimensions, typography and similar design decisions; it is **not** a schema for a component's composition, a specimen card, or an entire board. Its companion resolver describes sets/themes if those become necessary, but v1 need not implement themes. [2](https://w3c.github.io/cg-reports/design-tokens/CG-FINAL-format-20251028/) [2](https://w3c.github.io/cg-reports/design-tokens/CG-FINAL-resolver-20251028/)
- **Structured board data:** JSON Schema draft 2020-12 provides a vocabulary for validating the structure and values of JSON data. We can define **our own versioned board document** (items, variants, states, sample text, token references, layout hints) and validate it; JSON Schema does **not** supply an industry-standard board vocabulary. YAML is an alternative human-authored serialization, but parsing it into JSON-shaped data still leaves us responsible for a board schema, semantics, diagnostics and safe validation. [1](https://json-schema.org/draft/2020-12/json-schema-validation) [1](https://www.loc.gov/preservation/digital/formats/fdd/fdd000645.shtml)
- **Markdown and metadata:** CommonMark is a prose syntax, not a typed component/board data model; YAML front matter is an application convention, **not part of CommonMark**. It works for narrative explanation, rationale and human-facing labels, but a board generator must define and validate any metadata and references it accepts. [1](https://talk.commonmark.org/t/front-matter-best-practice/2235) [1](https://jekyllrb.com/docs/front-matter/)
- **Code-backed component cases:** Storybook's Component Story Format (CSF) represents component stories/states as ES modules with component metadata and args. It can be a useful **later import adapter** when an actual application and its components already exist; it is not a neutral source for a documentation-only or greenfield board utility, and rendering those stories would require the relevant component/framework runtime. [1](https://storybook.js.org/docs/api/csf)
- **Output:** SVG 2 defines vector graphics, text, and `title`/`desc` elements for text alternatives. Export should use meaningful groups/text/shapes and a viewBox rather than flatten everything into a bitmap. The SVG standard does not define the upstream board authoring model. [1](https://svgwg.org/svg2-draft/single-page.html)

## Candidate canonical input arrangements

| Choice | Good for | Cost / limitation | Fit for first atlas slice |
| --- | --- | --- | --- |
| **A. Markdown-only**, with headings/tables and perhaps YAML front matter | Easy to write and review as prose; accepts existing design docs | Layout/state fields become implicit conventions; ambiguous Markdown and prose cannot deterministically encode all specimen geometry; front matter needs a custom schema | Viable only with a deliberately small, strictly validated convention and visible unresolved fields; not a universal Markdown-to-design promise |
| **B. JSON or YAML-only**, using a custom versioned schema | Reliable validation, editor form generation, deterministic render inputs and diffable fixtures | More verbose for explanatory prose; custom schema still required; YAML parsing/conventions require care | Strong for geometry and states, but should not force all design rationale into data fields |
| **C. Hybrid: DTCG token JSON + versioned board manifests (JSON or YAML) + optional Markdown notes** | Keeps portable tokens separate from project-specific layout/content; typed/validatable rendering and readable narrative; GUI can edit the same sources | Multiple file types and references must be explained; careful diagnostics and single-source-of-truth rules required | **Recommended proposal**: one small specimen manifest, one token file, optional linked notes; do not build a general design-language compiler first |
| **D. Code-first stories (e.g. CSF) + tokens** | Existing implemented components with real props/states | Runtime/framework coupling; not a greenfield/docs-only interchange | Defer as optional brownfield importer, not the first source of truth |
| **E. Existing SVG templates as canonical input** | Fast visual duplication | Copies content/style assumptions; weak semantic round-trip from design docs; templates drift as specs change | Keep supplied SVGs as visual references, not editable canonical source |

## Provisional design experiment, not a chosen format

Build a tiny **three-way authoring spike**, not three full renderers: represent the *same* token set, one primitive with two states, one component, and one board title in (A) Markdown with front matter, (B) one JSON/YAML manifest, and (C) DTCG tokens plus a small manifest and optional Markdown note. In each case check: can a human change a label/token/state unambiguously; can the tool report a missing token and a conflicting status; can an editor round-trip without discarding authored notes; can the same input render the same SVG and preserve editable text/shapes? Show the owner the files and one rendered board before choosing a canonical source. Avoid putting brand-specific material from the private references into the public spike.

**Recommendation to test:** use DTCG JSON **for tokens**, not for the whole design system; define a **small versioned, validated board manifest** for deterministic specimen composition; retain Markdown for narrative, rationale and optional annotations. Choose JSON versus YAML for the manifest only after the owner tries the authoring spike. Generated SVG is output, not the source of truth. If the spike shows Markdown plus a tiny validated front matter is simpler without ambiguity, prefer that rather than forcing three formats. Do not claim any project-specific board schema is an established standard.

Still open: who authors and edits the canonical files in v1; whether a GUI must preserve byte-level prose formatting or only semantic fields; exact constraints on free-form content, token references and layout defaults; what is visually acceptable; and whether a local web or desktop UI is the better wrapper. These are guided-journey decisions, **not** requirements to guess from the standard documents.
