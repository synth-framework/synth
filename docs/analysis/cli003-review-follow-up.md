This narrows the intermittent failure, but does not imply the production CLI removes Git metadata: the subtest calls `fs.rm(root, { recursive: true, force: true })` between synchronous CLI subprocesses and then restores a snapshot. Node's recursive removal can itself report a descendant `rmdir` failure when `.git/info` changes during traversal. The pause handler has no `.git/info` cleanup.

The correction is limited to disposal of the parity test's **temporary fixture**: use Node's bounded `fs.rm` retry options (`maxRetries: 10`, `retryDelay: 100`) for its snapshot/root/outer recursive removals. This retries transient `ENOTEMPTY` rather than ignoring a persistent failure. It does **not** remove `.git/info` in product code, run `git clean`/`reset`, relax output/state/commit parity assertions, or modify any project governance state. A focused cleanup-options test plus the full parity suite passed locally under Node 22 (49/49) and Node 20 (49/49). A new CI run is still required; absolute timing acceptance remains unmet.

## Clean-status adapter-loading candidate (after `45f04f6`)

A status graph audit found that `resolveGovernanceContext()` and `buildOperatorBriefing()` constructed the default Mission Studio adapter registry solely to obtain `list()` for capability availability. The default registry now seeds its factory map in the order of one frozen planning-adapter name list, and its `Record<PlanningAdapterName, AdapterConstructor>` type rejects missing/extra factories at compile time. Both read-only projections consume the same list. `AdapterRegistry` still constructs real adapters for actual work; no mock availability, cached project state, skipped replay, or CLI verb was introduced.
