# Proposed Expedition B — test the guided journey end to end

**Status: reviewable charter proposal, NOT a canonical Expedition, approval, commit or start.** No ID is assigned. This is the independent acceptance/evaluation workstream for [the scoped SYNTH build charter](guided-journey-synth-build-charter.md), under the proposed Mission in [the recovery plan](guided-intent-recovery-expeditions.md). It may define fixtures and record today's failures **before** build work; its final owner pilot depends on the build path being runnable. Never run the actual pilot or publish the owner's private reference SVGs without consent.

## Question and method

Does the shipped SYNTH-guided, human–agent journey produce a *more grounded, easier-to-follow and more truthful* brief → plan → tested outcome than the same agent with a short written spec and ordinary Git/PR/CI? This tests guidance and traceability, **not** absolute prevention of agent action or SYNTH-generated application code. Keep the agent/tool optional in the fixture harness; identify it precisely in the real pilot when the owner selects one. Pre-register tasks, success/failure and observations before implementation or pilot execution.

## Executable protocol and evidence

1. **Freeze the control:** a plain agent + short written spec + normal Git/PR/CI workflow with the same scoped SVG utility task. Record agent, initial inputs, elapsed time, clarification requests, wrong assumptions and final checks. The synthetic control is an engineering diagnostic; do not claim user-value findings until the real owner pilot runs.
2. **Capture baseline failures and define assertions:** run shipped `first-contact --dry-run`, `discover . --export` for brownfield, `docs generate` with the actual `docs/` or explicit `knowledge/` source, and first-contact or correctly aligned Mission flow. Preserve exit codes, exact source file names/counts, decisions, previews, event/state checks and separate agent-authored notes. Existing E2E evidence is a starting observation, not a passing acceptance test. Make tests initially red where current behavior is wrong, without weakening older checks or fabricating a human reviewer.
3. **Acceptance assertions after build:** source facts versus proposals versus confirmed choices are visible; substantive unknowns prompt options; the wrong template is rejected; Mission/plan/acceptance checks follow the same brief; replay **and** `verify` agree after materialization. Absence of a Git diff must say *not checked* rather than claiming validated code; a delegated test run must say it was delegated. Negative cases include conflicting docs, missing intended knowledge sources, unsupported input, unrecognized architecture, and unapproved agent interpretation. Avoid a test that passes solely because JSON was emitted or a journal replays.
4. **Functional SVG pilot only after owner review:** with an as-yet-undetermined agent selected by the owner, use the agreed hybrid source direction and a deliberately small *non-private or owner-approved* example (one token set, one primitive with two states, one component). Run import → preview normalized mapping/provenance and unresolved fields → owner review → save standardized token/board/notes files → render an editable SVG board. Check original sources unchanged, malformed token references/duplicate IDs/conflicts detected, no clipped essential labels in the reviewed example, and that altering a label/token changes the expected board. The reference SVGs are a visual quality bar, not pixel-identical goldens or permission to redistribute them. The product app is **agent-written**; separately identify what SYNTH contributed.
5. **Git-backed evidence and matched comparison:** use a real reviewable change with ordinary PR semantics; tie assertions to the exact source revision and distinguish branch, PR and published base. If branch integration is blocked, report the concrete reason/recovery and stop—do not add a shared ledger ritual, hand-edit governance state or claim a merged outcome. Repeat the scoped request through the plain-spec control, log interventions and operator effort, and ask the owner which treatment preserved intent better. A single owner pilot is diagnostic, not a population claim; unfamiliar operators may be studied separately.

## Result format and gates

Publish one test report with a row per path and per treatment: **input, agent/tool/version, human versus synthetic decisions, sources consumed, questions asked, brief and plan produced, code author, application tests actually run, SYNTH replay/verify results, PR revision/publication state, timing/interventions, limitations**. Mark each requirement `pass`, `fail`, `blocked` or `not run` and link to the relevant file/command/output. Do not summarize a delegated `npm test` as full SYNTH governance or turn a successful SVG render into a lifecycle certificate.

**Initial gate:** the owner reviews the interaction contract and synthetic fixtures; their private material is excluded by default. **Build gate:** the first three path assertions and negative cases run against the current shipped CLI and record actual failures; the build charter can then repair them one slice at a time. **Pilot gate:** the owner selects an agent and authorizes a real task/repository and example inputs; no synthetic choice is relabelled as owner approval. **Outcome gate:** if SYNTH fails to improve consequential guidance or truthfulness relative to the control at tolerable operator effort, recommend simplification instead of expanding governance. Do not claim completion if materialization Drift or architecture/template mismatch remains.

**Scope exclusions:** no implementation of the SVG editor or renderer inside the SYNTH checkout; no hosted deployment/security certification; no new approval verb or protected-branch workaround; no rerunning unrelated full suites to mask targeted failures. Coordinate with the build charter's immediate blast radius and LIFE-002's separate Git integration work.
