## Mission meaning to confirm or change

SYNTH should guide a human and coding agent from an ambiguous idea, root-level existing project, or `docs/`/`knowledge/` inputs to a *scoped, revisable* build brief and an aligned, verifiable plan. Questions and options should be contextual to actual evidence; distinguish source observations, agent inferences, the exact offer, original human words, delegated/provisional choices, and later reviewer decisions. The agent may write code with normal tools and proceed on reversible choices while preserving reasons. SYNTH is decision support and traceability, **not** a universal pre-execution lock, application code generator, cryptographic human-identity verifier, or second Git promotion system. Ordinary PR review happens **before Git merge**; Git facts and CLI role flags do not themselves authorize human choices. At the Mission horizon, compare an eventual owner-run SVG-board pilot with an ordinary agent + concise spec + Git/CI control, then decide whether to keep, simplify or replace the guided path; that pilot needs separate owner selection of an agent and authorization of inputs.

## Why the runtime start remains pending

The planning draft is present on `main`, but the current runtime has no approved guided Mission. The existing two approved Alignment Contracts are unrelated to this Mission and recorded with `synth-cli-operator` as a purported human reviewer. The supported full `intent refine` / `intent approve` / `alignment create` / `alignment approve` route currently hard-codes that reviewer, substitutes Mission Studio homepage behaviors/evidence and placeholder file hashes/scores when defaults are used. `alignment prepare` has the same truth problem. Reusing any of those records would make a false alignment claim. `expedition create` can append `EXPEDITION_CREATED` without a valid runtime parent; using this planning draft or the active Framework Maturation Mission would misattribute or orphan the new Expedition. CLI-003 still reports `executing` despite its PR being merged; do not use `--complete-first` to close unrelated work. The CLI approval preflight now targets the verified draft's Mission and requires an explicitly selected Alignment Contract rather than the latest one by recency. This prevents one wrong-parent gate and inference path, but does **not** prove a selected contract's relevance or supply authentic review evidence. The existing first-contact GitHub lookup reads formal PR review objects, not PR conversation comments; it cannot currently consume `jtanori`'s chosen alignment-response channel. Do not mark alignment confirmed from that lookup or a CLI human label. A comment must be examined as account-attributed evidence against the actual reviewed scope, and a truthful bridge to the relevant Intent/Alignment Contract is still needed.

**Unblock condition:** a source-grounded Intent/Alignment Contract for this exact reviewed scope, with the response attributed through the chosen account-attributed PR comment channel and no canned evidence, passes the Mission approval/branch gates on the correctly owned checkout. Check the actual branch and intended base against the declared owned branch **before and after** any approval path; `--no-create` prevents branch creation, not a checkout switch. The revised `--complete-first` is Mission-scoped but still invokes `force: true` for a same-Mission Expedition; it is not evidence of completion and must not be used to clear a gate.
