## Mission meaning to confirm or change

SYNTH should guide a human and coding agent from an ambiguous idea, root-level existing project, or `docs/`/`knowledge/` inputs to a *scoped, revisable* build brief and an aligned, verifiable plan. Questions and options should be contextual to actual evidence; distinguish source observations, agent inferences, the exact offer, original human words, delegated/provisional choices, and later reviewer decisions. The agent may write code with normal tools and proceed on reversible choices while preserving reasons. SYNTH is decision support and traceability, **not** a universal pre-execution lock, application code generator, cryptographic human-identity verifier, or second Git promotion system. Ordinary PR review happens **before Git merge**; Git facts and CLI role flags do not themselves authorize human choices.

**First Expedition proposed for later runtime start:** Three-path acceptance and contextual offers. Begin with red synthetic fixtures for empty idea, existing root application with tests, and competing `docs/` / `knowledge/` statements; then make bounded source-linked questions/options/trade-offs available without asserting semantic understanding or fabricating answers. Preserve existing behavior and prior branch-local source/choice/brief slices. No real owner SVG pilot, universal architecture rewrite, runtime approval/start, or merge is part of this first Expedition's acceptance.

**Open human decisions for review:** Is that Mission purpose and first-Expedition scope what you intend? Which GitHub account(s), if any, may provide an account-attributed approval of this Mission's alignment record? A review of this document can identify the owner/designated account and any edits needed. Account attribution is not proof a person was at the keyboard.

## Why the runtime start remains pending

The planning draft is present on `main`, but the current runtime has no approved guided Mission. The existing two approved Alignment Contracts are unrelated to this Mission and recorded with `synth-cli-operator` as a purported human reviewer. The supported full `intent refine` / `intent approve` / `alignment create` / `alignment approve` route currently hard-codes that reviewer, substitutes Mission Studio homepage behaviors/evidence and placeholder file hashes/scores when defaults are used. `alignment prepare` has the same truth problem. Reusing any of those records would make a false alignment claim. `expedition create` can append `EXPEDITION_CREATED` without a valid runtime parent; using this planning draft or the active Framework Maturation Mission would misattribute or orphan the new Expedition. CLI-003 still reports `executing` despite its PR being merged; do not use `--complete-first` to close unrelated work. The CLI approval preflight now targets the verified draft's Mission and requires an explicitly selected Alignment Contract rather than the latest one by recency. This prevents one wrong-parent gate and inference path, but does **not** prove a selected contract's relevance or supply authentic review evidence.

**Unblock condition:** a source-grounded Intent/Alignment Contract for this exact reviewed scope, with the response attributed through a real review channel and no canned evidence, passes the Mission approval/branch gates on the correctly owned checkout. Capture the actual returned runtime Mission ID, verify replay/`verify`, then create, review and separately start Expedition 1 under that ID. Until the code can represent this truthfully, the first Expedition's synthetic test preparation may continue as branch-local work, but not as a claimed started runtime Expedition.
