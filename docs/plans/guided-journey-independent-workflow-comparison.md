# Guided journey: independent workflow proposal vs. SYNTH today

**Status (2026-10-15): proposal for owner discussion, not an approved product contract, runtime Mission/Expedition, implementation authorization, or pilot result.** Comparison based on the independent human–agent workflow described in this conversation, *then* checked against this branch at `710139bcc6d6`. The proposal is deliberately not derived from the current command hierarchy. Keep the previously accepted [build](guided-journey-synth-build-charter.md) and [test](guided-journey-test-charter.md) review scopes as separate references; this document may prompt their revision **after** discussion, not silently replace them.

**Owner directions during review:** requirements and specifications evolve; humans do not settle everything before starting. The agent may make a choice and proceed while keeping that choice **open**, with its reason recoverable when work is consolidated. A trivial choice may simply be recorded; a more-than-trivial choice needs someone (the owner suggested a human) to decide whether to keep it or choose differently. Thus “agreement” below means a **current, scoped working agreement sufficient for the next slice**, not a frozen complete specification. The owner clarified that **consolidation happens in ordinary review before the change is merged in Git**; it is not a second post-merge ceremony. The thresholds, record format and reviewer authority below are still proposals for discussion.

## 1. The workflow I would want as a coding agent

1. **Orient:** capture the person's original request verbatim; inspect the actual idea, documents, code and tests. Report observed facts with references, interpretations as proposals, and unknowns as unknowns. Preserve working behaviour in an existing project. An empty idea needs no invented repository facts.
2. **Clarify what matters, but allow provisional choices:** ask a small, contextual batch when a choice matters now. The person can choose, delegate a bounded decision, or defer it. The agent may choose and implement a reversible approach while keeping that choice **open and attributed to the agent**, with its reason and alternatives recoverable for later consolidation. An exploratory prototype is evidence for discussion, not a human-approved deliverable.
3. **Agree *enough* for the next slice:** a few paragraphs for a small change or a versioned document for larger work: outcome, users, the **current** slice, non-goals for that slice, decisions that matter now, constraints, open questions and observable acceptance examples. Unknowns may stay open while reversible work proceeds; they must not be described as settled. The agent drafts; the person confirms the *meaning* of commitments they settle, while still-open agent choices remain labelled as such—not every command needs human review.
4. **Plan and implement a thin slice:** preserve existing capabilities, state expected changes and checks, write application code with ordinary tools, and pause before irreversible/costly/sensitive acts. Use prototypes and demonstrations to learn what the person actually wants. When feedback or new evidence changes a consequential commitment, revise the **working** brief visibly for the affected scope instead of quietly reinterpreting it; ordinary Git/PR/CI still publishes the change.
5. **Compare, learn, revise:** demonstrate user scenarios and distinguish checks actually run (with revision/result) from delegated, failed, unavailable and not-run checks. Compare the outcome with the brief **as it stood when that slice was built**; record newly requested behaviour for the next revision rather than retroactively making the old result a lie. Surface deviations and outstanding decisions, then repeat the loop.

The companion CLI's job would be **durable project memory plus a small, current context packet** for the agent and person—not a 1,000-line instruction file and not an assertion that it controls everything an arbitrary agent does. The packet should identify its branch/revision, goal, relevant evidence, confirmed choices, open decisions, current brief, checks and most useful next question/action; detailed records remain queryable by ID. A tiny generated agent bootstrap or tool integration could instruct the agent to consult it at session start, after meaningful scope/branch changes and before claiming completion. The agent still inspects sources and reasons; the CLI records typed facts and checks mechanical consistency; the human owns consequential choices.

### Determinism and drift contract

**Make commitments deterministic, not model prose.** Preserve separately (a) exact original human request, (b) the *exact offer displayed*—question, option texts, trade-offs, recommendation and version—(c) the original human answer and its provenance, (d) the resulting human choice, bounded delegation or deferral, and (e) any *agent-made, still-open choice* with its reason and eventual review outcome. An agent interpretation of an ambiguous answer remains a proposal. An edited offer or revised decision supersedes, rather than silently overwrites, what was previously shown. Link claims to source paths/line ranges plus file content identity and, when available, repository revision; changes make dependent claims *stale for review*, not retroactively false or automatically reapproved. A reproducible brief distinguishes confirmed commitments from open agent choices; AI-authored wording can vary before confirmation.

Reduce drift with a compact, revision-pinned context at session restart and a stated intended delta before work. Detect it with explicit trace links from source/decision to brief, plan, changed behaviour and acceptance examples. Contain it with small demonstrations, human review of consequential deviations and checks tied to the actual code revision. Only mechanically supportable claims (e.g. recorded option version, intact source reference, executed check and its exit status) are mechanically certified. Semantic agreement and code correctness cannot be guaranteed by a CLI; an agent can act outside it. Do **not** turn this into a blanket pre-execution lock or a false identity/approval guarantee. For meaningful human attribution, a trusted UI/channel or confirmation of the proposed decision record is needed; an agent-supplied `actor: human` label alone is not evidence.

### Evolution is the normal loop, not an exception

A brief is a **versioned working agreement for a slice**. It says which commitments are confirmed *for now*, which are provisional/delegated, and which questions can safely remain open. A person can change their mind after seeing a prototype; a source can change; the team can discover a constraint. None of that is automatically agent drift. Drift is **silently changing a commitment, erasing the earlier choice, or reporting new work as if it met an agreement it did not**.

Proposed low-friction change loop:

1. **Observe:** capture the new request, result or source change in its original form. Distinguish a new requirement from a bug in the current implementation, a clarification of an existing choice and a merely exploratory idea.
2. **Show the delta:** state the old commitment, proposed new one, why it changed, which behaviours/acceptance examples and files or plans are affected, and what can remain unchanged. The agent recommends a path when warranted; it does not relabel its suggestion as the person's choice.
3. **Decide provisionally when safe:** the agent can choose a reversible path and continue without pretending it is a human decision. Preserve its rationale and any affected assumptions for later review. If the action itself is irreversible, privacy-sensitive, externally visible or expensive, ask *before* acting. Otherwise, product-affecting agent choices stay open until consolidation; no new approval ceremony for every minor refinement.
4. **Supersede, don't rewrite:** keep the original offer, answer and old brief/check results accessible; link the newer decision and brief revision to them. The new revision governs *subsequent* work. A changed source marks dependent interpretations as needing review; it does not automatically negate every unrelated choice.
5. **Recheck only the affected scope:** update impacted examples/tests and make stale verification visible. An old test result remains evidence for its old code and brief revision, not a pass for the new one. The context packet should say **what changed since the agent last looked** and what decision, if any, is now needed.

Example: if the first agreed slice exports one artifact and, after seeing it, the person asks for batch export, preserve the one-artifact slice and its checks as historical truth. Propose batch export as the next scoped revision, identify any change to the input model and tests, and keep any agent-chosen approach visible as provisional until reviewed. This avoids both a frozen upfront spec and moving the original acceptance goalposts silently.

### Provisional agent choice → consolidation review (owner direction; mechanism proposed)

A decision can be **implemented but still open**. The minimal record should identify the choice, the agent who made it, why it seemed reasonable, the alternatives considered, the source/brief revision it relied on, what would change if reversed, and the checks run. Do not capture every keystroke or variable name: record choices that another worker might reasonably need to understand or reconsider. The context packet should show *open agent choices and their reasons*, not silently promote them to human requirements.

**Consolidation is the ordinary review of the proposed change before its Git merge** (for example, during PR review). A human or another agent can retrieve the rationale and assess impact there. Reviewing a product choice is not itself a Git merge: the change only becomes part of the target branch when Git actually merges it. Where there is no Git repository, use the equivalent review before treating the work as the new baseline; do not invent a merge. Proposed triage:

- **Trivial to keep or change:** record that assessment and the agent's reason; mark the choice settled for this slice as an **agent choice**, not as a human-selected product requirement. A reviewer can always escalate it.
- **More than trivial to keep or reverse:** present the trade-off, affected behaviour and rework cost to a human. They choose **retain**, **change** or **defer**. If deferred, the affected design remains provisional and is not reported as fully agreed. Another agent may prepare this review but must not impersonate the human decision.
- **Sensitive or irreversible in the act itself:** request authorization *before* doing it; deferring review until consolidation is not sufficient.

“Trivial” is about **impact and reversibility**, not line count: a one-line change to persistence, a public input format or privacy may be substantial. Conversely, a fairly large but isolated, reversible layout implementation may be routine. The exact thresholds and reviewer authority remain to be agreed with the owner. If a material choice is deferred at pre-merge review, the review must make its disposition explicit: revise or exclude the affected work, or deliberately retain it as labelled exploratory scope—not describe it as a settled product commitment. This is a review of the **product choice within the normal Git workflow**, not a demand to perform an extra `deliver`/`seal` sequence after an ordinary PR merge.

## 4. Questions for our review (proposed defaults, not settled decisions)

1. **When is an agent choice ready to be settled?** Owner direction: allow the agent to decide and proceed while leaving the choice open, then recover its rationale at consolidation; record trivial choices, and bring more-than-trivial ones to a human for retain/change/defer. Proposed default: assess impact and cost to reverse, not code size; obtain prior consent for sensitive or irreversible acts. Consolidation is the ordinary review **before Git merge**; who may classify a choice as trivial, and when must the human make the final call?
2. **What is enough agreement to begin, and how should it evolve?** Proposed default: a working brief for the next slice whose consequential statements refer to the exact offer, your original response or explicit delegation, and supporting sources. Unresolved future questions are allowed; a new consequential choice revises the affected commitments without rewriting the old offer, the old outcome, or unrelated work. A generic field-completion score alone is insufficient. How should an open agent choice appear in that brief while useful work proceeds?
3. **How should a CLI recognize your response?** Proposed default: preserve raw text and the displayed offer; if the only channel is an agent relaying your words, require explicit confirmation before attributing a consequential choice to you. Do not claim cryptographic identity from a role string.
4. **How much agent-facing instruction is acceptable?** Proposed default: tiny generated bootstrap plus a typed, compact context packet from existing read surfaces; any migration from the current generated `AGENTS.md` needs evidence that safety requirements survive and agents actually retrieve the packet.
5. **What would disprove the proposal?** Proposed default: matched pilot shows no better decisions or fewer mistakes than an agent + concise spec, but adds more operator work; simplify instead of layering more ceremonies.
